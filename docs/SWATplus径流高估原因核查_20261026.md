# SWAT+径流高估106.89%的原因核查（2026-10-26）

**结论：主要问题是工程的水量路由配置，不能仅归为“没率定”。三条汇流单元将同一种`tot`水量以0.7送河道、0.3送塘库，同时又以1.0送含水层；含水层把它当补给，再出流回河道，形成重复计水。** 单位换算和现有资料内的出口配对未发现错误，缺测生成的降水规模不足以解释翻倍偏差。含水层初值另有明显不合理之处，须在后续修复中检查。本轮没有修改这些配置或参数。

上轮“程序、输出和评价链路可运行”的结论仍成立；**不能把该案例认定为物理有效、可直接用于正式融合比较的模型基线**。原始失败、成功运行、观测、106.89%偏差全部保留，本报告是补充纠正，不撤换负结果。

## 1. 本轮范围与证据

核对固定LREW工程、同流域观测、原生输出、平台基线解析脚本，并查找同修订号源码。只在新副本`runs/lrew_water_audit`打开更多日/年输出，原生SWAT+59.3退出0。真正的工程输入除`print.prt`外逐文件与原始包一致；该诊断副本的`channel_day.txt`与前次基线逐字节一致。

源码来自[保留59.3历史的仓库提交](https://github.com/dhardestylewis/swatplus_predocker/tree/7076625db0a2c9fb88efaf60d55fa3b296c4a3a1/source_codes)，`main.f90`明确为`SWAT+ Jun 28 2019 MODULAR Rev 2019.59.3`，与运行输出的版本、日期一致。URL及SHA256保存在`bias_audit/source59_provenance.json`。这是同版本历史源码交叉核验；未从该源码重编译并证明二进制构建完全一致，不混同版本标签匹配与完整构建溯源。

## 2. 单位核查：未发现换算错误

`channel_control.f90:279–282`将内部日水量m³除以10000写入`ch_d%flo_out`，`channel_output.f90`直接将该日值写入输出。因而本版日`flo_out`确为ha-m，不是m³/s。此前使用：

`日均流量(m³/s) = flo_out(ha-m/日) × 10000 / 86400`

换算与源码一致，体积累计也用逐日值还原。没有重复乘流域面积，亦未把月均或年均当日值。观测m³/s单位由上游[SWATrunR源文档](https://github.com/chrisschuerz/SWATrunR/blob/master/vignettes/SWATrunR.Rmd)确认。

另发现旧版本部分其他输出的单位标题不能直接相信：如`ru_yr.txt`把流量标m³/s，但`ru_control`将多个水文分量累计进`ru_d`，不宜直接用这个字段做总产水。下文使用陆地`wateryld`、含水层`flo/rchrg`及面积换算，不拿RU总字段反推水量。含水层的`flo_cha`标题也与源码量纲有出入，故预算采用明确的`flo(mm)`。

## 3. 出口与观测配对：现有证据支持，原始质量复审仍缺

- 上游SWATdata明确将工程和观测都标为LREW gauge J上游流域；未跨流域拼接。
- 本工程`channel.con`中2、3汇入1，1无下游连接，故选择1；不是尝试各条河道后选拟合最好者。
- 原生结果2003-01-01—2012-12-31，观测日期转换后逐日匹配3653天，无重复或缺日，零观测保留，没有擅自当缺失剔除。
- 同日相关系数0.863824；作为时间错位诊断，检查±1、±2天，同日相关性最高。没有按此移动时间来优化指标。这支持不存在明显整日错位，但不单凭相关系数证明测站数据完全正确。
- RDS没有逐日质量旗标，尚未独立取回原始测站记录复审。因此不能完全排除观测层面的未知问题；当前没有证据将106.89%归因于出口错配。

## 4. 缺测处理：确认调用天气发生器，规模很小

同版`climate_control.f90:105–120`明确：日降水`<= -97`时调用`cli_pgen`，不是直接把-99参与产流；`cli_pgen.f90`提供随机生成降水。

2003—2012年11个站日缺测：2007-03-02/03，2009-06-18至24，2009-12-14/15。保留原工程默认种子与处理。依据`hru.con`的真实站点面积权重：sta01=0.3965575、sta02=0.2415617、sta03=0.3618808。

将模型日流域降水减去其他非缺测站的面积加权降水，反推这些缺测站的贡献，得到：

- 十年生成降水贡献约**4.5094毫米（流域陆地面积平均）**；原生输出四舍五入会使个别反推值出现约0.001毫米的微小负值，不应解释为生成了负降水。
- 同期总降水10936.283毫米，生成部分约**0.0412%**。
- 按2143.8ha陆地面积折算约**9.67万m³输入水量**，而出口高估约6678.95万m³。
- 2003—2006等没有这些降水缺测的年份同样明显高估。

因此缺测处理需要记录，但没有依据把接近翻倍的系统偏差归给这11天。9.67万m³是新增降水的量级比较，不是严格的径流反事实上界；未改缺测处理重跑来做因果估计。逐日反推记录在`missing_precipitation_trace.csv`。

## 5. 主要原因：同一种水量被重复分配

工程`rout_unit.con:3–5`三个汇流单元均如此：

| 接收对象 | 水文类型 | 分配比例 |
|---|---|---:|
| 河道cha | tot | 0.7 |
| 含水层aqu | tot | 1.0 |
| 塘库res | tot | 0.3 |

这里不是不同水文分量分别取1.0，而是**相同`tot`分量累计分配2.0**。正常需要区分河道/塘库的地表及侧向产水与含水层的底部补给，不能一律`tot`。

同版源码链条：

1. `hru_hyds.f90:87`将土层底部渗漏单独放入`hd(2)`；119–123行把地表、侧向及排水`hd(3:5)`合为`hd(1)`。因此`tot`不含底部补给。
2. `ru_control.f90`分别汇总这些水文分量，没有把它们重新分成可供再次计量的不同水源。
3. `hyd_connect.f90:290–300`把`tot`映射到`hd(1)`、`rhg`映射到`hd(2)`；不会因为接收者是含水层便自动把`tot`改为补给类型。
4. `command.f90:124–128`对非HRU接收者按指定分量乘分配比例，再累加到接收水量；没有在三条`tot`出边之间自动归一化或扣减。
5. `aqu_1d_control.f90:39–54`将所有来水除以含水层面积变成补给，加入储量，再计算出流；`aquifer.con`把该出流送回河道。

这就把本来已通过0.7+0.3分给河道和塘库的陆地产水，再以1.0当作含水层补给，延迟后再次送入河道。是工程连线/水文语义错误，不是RMSE/PBIAS公式错，也不是给参数找一组更合适数值便能解释过去。

## 6. 输出水量证实了这条路径

统计2003—2012年，使用逐年陆地mm×2143.8ha×10以及含水层mm×各自面积×10，数值存在原生输出舍入误差：

| 水量 | 十年累计（万m³） |
|---|---:|
| 陆地产水wateryld | 6423.84 |
| 含水层收到的补给rchrg | 6423.63 |
| 含水层出流flo | 6450.02 |
| 模拟出口 | 12927.31 |
| 实测出口 | 6248.36 |
| 出口高估 | 6678.95 |

同时，十年每年陆地`perc`均为0，但含水层仍收到约等于全部陆地产水的补给，比例0.999966。模拟出口约等于陆地产水加含水层出流，两者之和与出口差约53.44万m³（出口的0.41%；塘库、河道储量及降雨蒸发等尚未逐项完全闭合），不是将内部误差假设为零。

含水层出流相当于总高估的96.57%，说明重复水量链路在量级上解释大部分偏差。**96.57%是诊断量级比，不是修复后效果保证；没有通过删除地下水出流来“修正”评价或宣称修复收益。** 原始逐年预算见`annual_water_budget.csv`。

## 7. 参数和版本语义的次要风险

按59.3的`aquifer_module.f90`字段顺序及`aqu_read.f90`整型读取，本工程三个含水层都被解释为：初始出流2500mm/日、含水层底深1000m、初始水位埋深1m、比出水率0.05。`aqu_initial.f90`据此计算初始储量49950mm。这些值对本流域明显可疑；文件创建于2018年，不能因为被打包为59.3示例就忽略旧输入语义。

原有3年预热后，评价期起点储量仍约1176—1185mm，终点约1007—1044mm。评价期合计储量下降约347.58万m³；同期深层渗漏约321.18万m³，因此这部分储量释放大部分被深层损失抵消，不能将十年6450万m³地下水出流都解释为初始储水排空：持续误接的6424万m³补给才是主体。

`file.cio`虽提及`calibration.cal`，包内并无此文件；`cal_parms.cal`只是可调参数范围清单，不是该流域已率定的证据。`hydrology.hyd`的perco=0、河道渗漏参数等也需要后续审查。没有上游率定日志，不能确认从未率定，但更不能把目前偏差简单归因于“只差率定”。
